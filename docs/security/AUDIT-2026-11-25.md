## 2. الثغرات المؤكدة والمُصلحة (Findings)

### SEC‑01 — تعطيل صامت لمحددات الطلبات في المصادقة عند غياب IP موثوق

| الحقل | التفصيل |
| --- | --- |
| **Vulnerability** | Fail‑open في تحديد المعدل (CWE‑770 / CWE‑307) |
| **Location** | `src/lib/security/auth-rate-limit.ts` → `enforceAuthRateLimit()` (سابقاً الأسطر 52–92) |
| **Severity** | **High** |
| **Why** | كانت دالة البناء `trustedClientIp()` تُرجع `null` إلا إذا فُعِّل `TRUST_PROXY_IP_HEADERS=true`؛ وعندها كان `enforceAuthRateLimit` **يتخطى** دلو الـ IP ودلو (IP+بريد) بالكامل. المسارات التي تمرّر `email: undefined` (استهلاك إعادة تعيين كلمة المرور، تحقق 2FA، بدء/عودة Google) كانت تُنتج خطة دلاء **فارغة** → لا حد إطلاقاً. |
| **Attack scenario** | عميل يرسل طلبات إلى `/api/auth/email/reset` برموز عشوائية: كل طلب يُقبل من المحدد، وكل طلب كان يُشغّل `scrypt` (≈16 MiB و عشرات الأجزاء من الثانية CPU) قبل التحقق من الرمز → إشباع threadpool/الذاكرة. وبالمثل يسقط سقف الـ IP عن تسجيل الدخول والتسجيل والتحقق. |
| **Fix applied** | استخراج التخطيط إلى وحدة نقية `src/lib/security/auth-rate-policy.ts` (`planAuthRateBuckets`) مع ثابت صارم: **الخطة لا تكون فارغة أبداً**. عند وجود IP موثوق تبقى الدلاء كما هي حرفياً. عند غيابه تُمنح المسارات التي لا تحمل بريداً دلوًا لكل عميل على بصمة رؤوس العميل الخشنة المستخدمة أصلاً في السلة/الدفع (`clientFingerprint`) — مفتاح تحديد معدل فقط وليس هوية — بحد `FALLBACK_CLIENT_MULTIPLIER × ipLimit`. أما طلبات البريد فلا تحصل **عمداً** على دلو بالبصمة: البصمة قابلة للتخمين (متصفح + لغة)، وربط الدلو الضيّق بها كان سيتيح لمهاجم حجب صاحب الحساب — وهو بالضبط ما يمنعه سقف البريد المرتفع الموثّق. لذلك يبقى سقف كل حساب هو الضابط المطبّق كما كان. `clientKey()` أصبح يستدعي نفس الدالة المشتركة. |
| **Files changed** | `auth-rate-policy.ts` (جديد)، `auth-rate-limit.ts`، `client-ip.ts`، `rate-limit.ts`، `.env.example`، `tests/security-regression.test.ts`، `tests/support/auth-rate-limit-probe.ts` |
| **Regression risk** | منخفض–متوسط ومُحيَّد: (1) سلوك بيئة الإنتاج المضبوطة (`TRUST_PROXY_IP_HEADERS=true`) مطابق تماماً لما قبل — مُثبت باختبار؛ (2) لا يُنشأ أي دلو بالبصمة لطلبات البريد → لا حجب متبادل ولا حجب موجّه لصاحب حساب؛ (3) مضاعف الدلو الاحتياطي مرتفع فوق أي حجم شرعي؛ (4) صيغة مفاتيح `clientKey` لم تتغير (`ip:` / `fp:`). |
| **Verification** | قبل: استجواب فعلي → **40/40 مسموح** بحد 20، و40/40 مع XFF مزيّف. بعد: استجواب داخل عملية فرعية يرفض الطلب عند تعذّر الوصول لمخزن الدلاء (fail‑closed). 7 اختبارات وحدة جديدة. تحكم سلبي: تعطيل الفرع الاحتياطي يُعيد إفشال الاختبار. |

> التفاصيل الكاملة: `docs/security/VULN-119.md`

### SEC‑02 — تضخيم استهلاك المعالج في استهلاك رمز إعادة تعيين كلمة المرور

| الحقل | التفصيل |
| --- | --- |
| **Vulnerability** | استهلاك موارد غير محكوم (CWE‑770) — KDF مكلف قبل التحقق من صحة المدخل |
| **Location** | `src/app/api/auth/email/reset/route.ts` → `POST()` |
| **Severity** | **Medium** |
| **Why** | كان `hashPassword()` (scrypt N=16384, r=8) يُنفَّذ **قبل** البحث عن الرمز، فيدفع الخادم الكلفة لأي طلب صحيح الشكل حتى لو كان الرمز غير موجود. |
| **Attack scenario** | إرسال رموز base64url عشوائية بطول 43 حرفاً: لا يُلمس أي حساب، لكن كل طلب يستهلك ذاكرة/CPU على الخادم فقط. |
| **Fix applied** | دالة جديدة `isConsumablePasswordReset()` تتحقق أولاً من الصيغة الصارمة ثم من وجود رمز غير مستهلك وغير منتهي بفهرس، ولا يُنفَّذ `hashPassword` إلا بعد نجاحها. الاستهلاك الذرّي الأصلي (قفل الصف + إبطال كل الجلسات) بقي كما هو. |
| **Files changed** | `src/lib/security/password-reset.ts`، `src/app/api/auth/email/reset/route.ts`، `tests/security-regression.test.ts`، `tests/support/password-reset-probe.ts` |
| **Regression risk** | منخفض: الصيغة وTTL وأحادية الاستخدام وإبطال الجلسات ونص الخطأ العام `RESET_TOKEN_INVALID` دون تغيير. |
| **Verification** | استجواب داخل عملية فرعية بلا `DATABASE_URL` + tripwire شبكي: كل الرموز المشوّهة تُرفض دون أي محاولة اتصال. اختبار بنيوي يثبّت الترتيب (محدد → فحص رمز → scrypt). اختبار حي: 403 بلا CSRF، و503 عام (fail‑closed) عند تعذّر مخزن الدلاء. |

> التفاصيل الكاملة: `docs/security/VULN-120.md`

### SEC‑03 — تجاوز حد الكوبون لكل مشترٍ للزائر عبر حذف كوكي السلة

| الحقل | التفصيل |
| --- | --- |
| **Vulnerability** | خلل منطق أعمال — تجاوز حد عبر حالة عميل قابلة للتبديل (CWE‑840) |
| **Location** | `src/lib/db/demo-order.ts` → `recordDemoOrder()`، اشتقاق `redeemerKey` |
| **Severity** | **Medium** |
| **Why** | مفتاح الاسترداد للزائر كان `sha256("guest-cart:" + cartId)`، والسلة تُنشأ من مجرد كوكي موقّع؛ حذف الكوكي = هوية جديدة ⇒ `perUserLimit` كان قابلاً للتطبيق على الحسابات المسجّلة فقط. |
| **Attack scenario** | تطبيق كود بحد استخدام واحد، إتمام طلب، حذف الكوكيز، التكرار: كل دورة تبدو كمشترٍ جديد وتستنزف أيضاً سقف `maxRedemptions` العام. |
| **Fix applied** | مفتاح الزائر أصبح `sha256("guest-email:" + email.trim().toLowerCase())` — 64 حرفاً hex تناسب تماماً `varchar(64)` ولا تتقاطع مع صيغة `user:<uuid>`. قفل صف الكوبون قبل العدّ بقي كما هو (تسلسل التزامن). |
| **Files changed** | `src/lib/db/demo-order.ts`، `tests/security-regression.test.ts` |
| **Regression risk** | منخفض: سلوك المسجّلين دون تغيير، والزوار يحتفظون بالميزة مع تطبيق القاعدة الموثّقة (رفض الاستخدام الثاني لنفس البريد عند بلوغ الحد). الصفوف التاريخية المفتاحَة بالسلة لا تُقرأ بالمفاتيح الجديدة. |
| **Verification** | اختبار تكامل PGlite على المخطط الحقيقي: سلة جديدة + نفس البريد (بصيغة مختلفة الأحرف والمسافات) ⇒ `invalid-promo`، وبريد مختلف ⇒ `recorded`. تحكم سلبي: إعادة المفتاح القديم تُفشل الاختبار. |

> التفاصيل الكاملة: `docs/security/VULN-121.md`

## 5. المخاطر المتبقية (Remaining Risks)

1. **غياب PostgreSQL حقيقي هنا:** القيود والـ Trigger وسلوك التزامن مُتحقَّق منها في CI على PostgreSQL 16 و/أو PGlite، وليس في هذه الجلسة.
2. **11 تنبيه اعتماديات moderate في أدوات التطوير:** `drizzle-kit`/`esbuild` (عبر `@esbuild-kit`) و`minimatch` (عبر سلسلة eslint). لا تعمل في زمن التشغيل المرفوع (`--omit=dev` = صفر)، ولا يوجد فيها high/critical. لم تُرقَّ عشوائياً لأن الترقية القسرية تكسر `db:generate`/الـ lint. التوصية: متابعة Dependabot (مُهيّأ أسبوعياً).
3. **الحاجة إلى `TRUST_PROXY_IP_HEADERS=true`** خلف وكيل عكسي للحصول على حدود IP/مصدر حقيقية. البديل الاحتياطي (بصمة الرؤوس) حدّ خشن قابل للتدوير، وليس بديلاً عن IP حقيقي، ولا يُستخدم في مسارات البريد تفادياً لحجب صاحب الحساب — موثّق الآن في `.env.example`. الأثر المتبقي: تسجيل الدخول بلا وكيل موثوق يبقى محدوداً بسقف كل بريد (60/15 دقيقة) لا بسقف لكل مصدر.
4. **سجلات Next.js لأخطاء Server Components** تُصدر نص الاستعلام و`params` بتنسيق الإطار نفسه (خارج `handleUnexpected`). التخفيف: ضبط مستوى السجلات لدى المزود والوصول المقيّد، وأي معالجة إضافية تتطلب طبقة إطار.
5. **تسجيل التسجيل الجماعي عبر SMTP:** إن لم يُفعّل IP موثوق، يبقى التسجيل الجماعي بعناوين مختلفة مقيّداً بسقف البريد لكل عنوان وحدود مزوّد SMTP (كل تسجيل يرسل رسالة فعلية).
6. **تراكم صفوف مجهولة المصدر:** `carts` بلا انتهاء، و`google_oauth_states` (10 دقائق)، و`auth_rate_limits` (تنظيف فرصي). لا توجد عملية تنظيف دورية موثّقة باك-end؛ التوصية بمهمة صيانة مجدولة.
7. **Webhook المحفظة بلا محدد معدل** (تحقق HMAC أولاً، 8 KiB، وكل محاولة فاشلة تكتب حدثاً تدقيقياً). حماية ضد التكرار تأتي من نافذة ±5 دقائق + مفتاح idempotency فريد. قدّرت أن إسقاط أحداث التدقيق أثناء العواصف يُضعف القدرة على الرصد، فتُرك كخطر متبقٍ بدل «إصلاح» يخفي الهجمات.
8. **إعدادات الاستضافة الخارجية** (TLS، قواعد الجدار الناري، حدود المزود، تدوير الأسرار) خارج نطاق المستودع.

## 7. الخلاصة المسنودة

تم إثبات **أربع** ثغرات حقيقية في الكود الحالي وإغلاقها جميعاً في هذا الفرع: تعطيل صامت لمحددات طلبات المصادقة (High)، تضخيم استهلاك المعالج عبر رمز إعادة التعيين (Medium)، تجاوز حد الكوبون للزوار (Medium)، وتسريب معاملات SQL في السجلات (Low). كل إصلاح مصحوب باختبار انحدار يفشل على الكود القديم وينجح على الجديد، وباستجوابات داخل عملية فرعية للمسارات التي تستورد `server-only`.

لم تُعثر ثغرات في بقية الفئات الـ35 بعد فحص فعلي، وتم توثيق أساس عدم الانطباق أو الدليل السلبي لكل منها. لا يمكن القول إن الموقع «آمن بالكامل»: ما يمكن قوله بدقة أن **الفئات المفحوصة أعلاه مغطاة بأدلة واختبارات**، وأن **المخاطر المتبقية في القسم 5 تبقى مفتوحة** وتحتاج معالجة تشغيلية خارج المستودع.
