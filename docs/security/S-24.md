# S-24 — Wallet ledger, top-up webhook, and promotion integrity

**Scope:** Wave 3B controls for customer wallet balances, signed provider top-ups, wallet-funded orders, and promo redemption.

## Controls implemented

- Wallet amounts are integer USD cents. One account row per user stores the current balance; ledger rows carry direction, positive amount, currency, order reference, and globally unique idempotency key.
- The `0008_wallet_ledger_and_promos` migration is additive. PostgreSQL constraints reject negative balances, non-positive ledger amounts, unsupported currencies/types, and invalid promo amounts. A database trigger rejects `UPDATE` and `DELETE` on ledger rows; reversals require compensating entries.
- `POST /api/webhooks/wallet-topup` reads bounded raw UTF-8 bytes, verifies HMAC-SHA256 over `<timestamp>.<raw body>`, compares signatures with `timingSafeEqual`, and enforces a five-minute timestamp window. Missing or malformed secrets/signatures fail closed. A transaction locks/creates the account, inserts the unique event ledger key, and increments balance only for the first event. Machine audit events are recorded without provider payload/PII.
- Authenticated wallet checkout serializes on the wallet-account row, checks sufficient balance, records paid order, order-item fulfillment allocation, stock decrement, ledger debit, and balance decrement in one transaction. The demo payment mode remains unpaid and non-production only. Checkout idempotency continues to protect duplicate order requests.
- Promo codes are NFKC-normalized and uppercased; all discount math uses integer cents and basis points. Validation is CSRF-protected, bounded, and rate-limited. Checkout re-locks the promo row and recomputes date, minimum, cap, global and redeemer limits before committing order and redemption together. Public offer display contains only active public codes.
- Wallet pages use authenticated user scope and private no-store caching; history is ordered and paginated. Checkout/promo labels and wallet history are bilingual.

## Operational requirements and residuals

- Set `WALLET_TOPUP_WEBHOOK_SECRET` to a random secret of at least 32 characters in production. Send a Unix timestamp and lowercase/uppercase hex HMAC in `X-Wallet-Timestamp` / `X-Wallet-Signature`. The signed bytes are exactly `timestamp + "." + raw JSON body`.
- A payment provider must only emit a credit event after it independently verifies settlement. This endpoint authenticates the sender but does not initiate or verify a provider-side charge.
- Wallet checkout requires enough encrypted fulfillment inventory; inventory allocation failure rolls back the order and debit. External top-up fulfillment providers remain outside this repository's scope.
- Local/CI tests do not prove provider, production secret rotation, or real-money settlement behavior. See Wave 3B verification record for actual checks and skipped tests.
