# VULN-119 — Auth rate limiting silently disabled without a trusted client IP

**Status:** FIXED (2026-11-25, branch `arena/ac3a149c-web-stor`)

| Field | Detail |
| --- | --- |
| **Vulnerability** | Missing/ineffective rate limiting — fail-open control (CWE-770 resource exhaustion, CWE-307 improper restriction of excessive authentication attempts) |
| **Location** | `src/lib/security/auth-rate-limit.ts` → `enforceAuthRateLimit()` (pre-fix lines 52–92); callers `/api/auth/email/reset`, `/api/auth/two-factor/verify`, `/api/auth/google/start`, `/api/auth/google/callback`, `/api/auth/email/{login,register,verify,resend,forgot}` |
| **Severity** | High (unauthenticated availability + credential-stuffing ceiling) |
| **Why it is vulnerable** | `enforceAuthRateLimit` took the per-client bucket and the client+account bucket only when `trustedClientIp()` returned an address, and that helper returns `null` unless `TRUST_PROXY_IP_HEADERS=true`. Routes that pass `email: undefined` (password-reset consumption, 2FA verification, OAuth start/callback) therefore computed an **empty** bucket plan and returned "allowed" without a single database write. With an email, only the loose per-email ceiling (e.g. 60/15 min for login) remained, so one source could run distributed-style stuffing unthrottled. |
| **Attack scenario** | A client that omits/ignores `X-Forwarded-For` (or any deployment that did not opt into trusted proxy headers) posts to `/api/auth/email/reset` with arbitrary tokens. Every request is accepted by the limiter, and each one previously ran a `scrypt` derivation (N=16384, r=8 → ≈16 MiB and tens of ms of CPU) before the token was even looked up, so a modest request rate saturates the libuv thread pool and memory. The same gap removes the per-IP ceiling from login/registration/verification endpoints. |
| **Fix applied** | Bucket planning was extracted into the pure module `src/lib/security/auth-rate-policy.ts` (`planAuthRateBuckets`) with a hard invariant: **the plan is never empty**. With a trusted IP the previous tight buckets are unchanged. Without one, identity-less routes get a per-client bucket on the coarse client-header fingerprint that cart/checkout already use (`clientFingerprint`) — never an address, never an identity signal — at `FALLBACK_CLIENT_MULTIPLIER × ipLimit`. Email-bearing routes deliberately receive **no** fingerprint bucket: a fingerprint is guessable (browser + locale), so binding the tight per-account bucket to it would let one attacker lock the real owner out, which is exactly what the documented high per-email ceiling prevents. For those routes the per-account ceiling remains the enforced control, unchanged from before. `clientKey()` in `rate-limit.ts` now delegates to the same shared helper, so one implementation exists. |
| **Files changed** | `src/lib/security/auth-rate-policy.ts` (new), `src/lib/security/auth-rate-limit.ts`, `src/lib/security/client-ip.ts` (`clientFingerprint`, `clientKeyFrom`), `src/lib/security/rate-limit.ts`, `.env.example` (documentation of the fallback), `tests/security-regression.test.ts`, `tests/support/auth-rate-limit-probe.ts` (new) |
| **Regression risk** | Low–Medium, mitigated: (1) with `TRUST_PROXY_IP_HEADERS=true` behaviour is byte-for-byte the previous bucket set — asserted by test; (2) email-bearing requests deliberately do **not** receive a shared per-fingerprint bucket, so no cross-visitor lockout is introduced; (3) the fallback multiplier keeps the coarse bucket far above legitimate volume, and email-bearing flows are untouched; (4) `clientKey()` output format (`ip:` / `fp:`) is unchanged, so existing stored buckets keep working. |
| **Verification performed** | (a) Pre-fix runtime probe: 40 sequential calls with no forwarding headers and `ipLimit: 20` → **40/40 allowed**; spoofed `X-Forwarded-For` with the proxy flag off → **40/40 allowed**. (b) Post-fix child-process probe (`tests/support/auth-rate-limit-probe.ts`) against an unreachable bucket store now **rejects** instead of allowing, i.e. the limit fails closed. (c) 7 new unit tests in `tests/security-regression.test.ts` cover the plan invariant, fingerprint stability, spoofed-header rejection, right-counted `X-Forwarded-For` under a trusted proxy, the guarantee that email-bearing flows gain no shared/guessable bucket, and the fail-closed probe. (d) Negative control: disabling the fallback branch makes the fail-closed test fail again. |
