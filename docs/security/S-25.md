# S-25 — Adversarial auto-ban shield, web-admin elimination, ephemeral hygiene and the owner CLI

**Status:** IMPLEMENTED (local verification only) — 2026-11-25, branch `arena/15ceef45-web-stor`.
**Scope:** removes the web administration surface, adds a two-tier adversarial auto-ban shield, bounded ephemeral-state hygiene, and a local-only owner operations CLI.

No production database, proxy, payment provider, SMTP server or OAuth provider was contacted. Every behavioural claim below was produced on a local instance with an unreachable database (to prove the fail-closed paths) and against a real embedded PostgreSQL (PGlite) for the data paths.

---

## 1. Web administration is gone

| Before | After |
| --- | --- |
| `src/app/admin/page.tsx` rendered an admin shell and returned `notFound()` for non-admins | The page is **deleted**. `src/proxy.ts` returns `404` for `/admin` and `/admin/**` for everyone, signed out or in, before any application code runs |
| Admin authorization relied on `users.role` + `ADMIN_EMAIL` | No web admin surface exists to authorize. `403` vs `404` timing/enumeration is no longer a question: there is one answer |
| `/api/admin/**` | Never existed; still absent |

- `classifyRequestPath()` normalizes the path (percent-decoding, duplicate slashes, `.`/`..` segments) and matches the **first segment**: `/admin`, `/ADMIN`, `//admin`, `/foo/../admin`, `/%61dmin` are all the same 404. `/administrator-guide` is a different path and is untouched.
- The 404 is `Cache-Control: private, no-store, no-cache, must-revalidate`, carries the same CSP and security headers as any other response, and has an **empty body** (no markup, no route hints, no framework error page).
- `/admin` is deliberately **not** a ban trigger: it is a known, removed surface that a curious visitor may probe, not an attack.
- `src/app/robots.ts` still disallows `/admin` so search engines forget it.
- Administration now happens locally: see §5.

Evidence: `threat-shield-db.test.ts` drives the real proxy function (`/admin` → `404`, empty body, `private, no-store`), and a live `next start` probe returned `404` with `private, no-store, no-cache, must-revalidate` for `/admin`, `/admin/users`.

## 2. Two-tier threat shield

New additive migration `0009_security_threat_shield` (mirrored in `src/lib/db/schema.ts`, `src/lib/db/migrations.ts` requirements, and the PGlite migration tests):

- `security_threat_events` — append-only adversary log: `actor_kind`, `actor_key`, `user_id`, `signal`, `tier`, `path`, `method`, `detail`, `occurred_at`. **No raw IP, cookie, token or email is ever stored.** Query strings are not stored at all.
- `security_bans` — one row per actor (`UNIQUE(actor_key)`), with `tier`, `signal`, `strikes`, `permanent`, `active`, `starts_at`, `last_strike_at`, `expires_at`, `lifted_at`. Database constraints enforce:
  - `actor_kind IN ('ip','fingerprint')` and `tier IN (1,2)`;
  - `strikes >= 1`;
  - `permanent = (expires_at IS NULL)`;
  - `expires_at > starts_at`.

`actor_key` is **NOT NULL by design**: a ban can only exist for an actor the proxy could actually identify.

### 2.1 Actor identity (zero-collateral first)

1. **Trusted IP** — only when `TRUST_PROXY_IP_HEADERS=true` *and* `trustedClientIp()` resolves a valid literal from the trusted hop count. Key: `ip:` + HMAC-SHA256(AUTH_SECRET, `ip\0<address>`).
2. **Header fingerprint** — otherwise, a salted HMAC over the client's **entire non-volatile header set** (sorted `name=value` pairs). Session-bearing, per-request, proxy-injected and Fetch-metadata headers are excluded, so the key is stable for one client across requests: cookie/host/content-*/origin/referer/accept/cache-control/range/x-forwarded-*/x-real-ip/x-request-id/x-nonce/next-router-prefetch/purpose/connection/sec-fetch-*.
3. **Nothing** — a request with no distinguishing header at all resolves to `kind: "unknown"`, `key: null`. It is logged, and **it can never be banned**. There is no `"unknown"`/`null`/`0.0.0.0` bucket, so one unattributable request cannot lock out a population.

An `X-Forwarded-For` value that is not configured as trusted is never treated as an IP; a malformed literal is not an IP either.

### 2.2 Tier 1 — certainty (immediate ban)

Signals: `scanner_path`, `honeypot`, `csrf_forgery`, `prototype_pollution`, `state_tampering`.

| Consecutive strikes (within 7 days) | Trusted IP | Header fingerprint |
| --- | --- | --- |
| 1 | 24 h | 24 h (recorded, not enforced — see below) |
| 2 | 7 days | 24 h |
| 3+ | **permanent** | 24 h |

- **Scanner/exploit families** (trapped in `src/proxy.ts`, before any routing): `/.env*`, `/.git*`, `/.svn*`, `/.hg*`, `/.aws*`, `/.ssh*`, `/.DS_Store`, `/wp-admin*`, `/wp-login.php`, `/wp-content*`, `/wp-includes*`, `/xmlrpc.php`, `/phpmyadmin*`, `/pma*`, `/myadmin*`, `/cgi-bin*`, `/actuator*`, `/server-status`, `/vendor/phpunit*`. Response: the same bare `404` + `private, no-store`, plus event + ban. Encoding and dot-segment tricks (`/%2eenv`, `//.env`, `/x/../.env`, `/.GIT/config`) are normalized first.
- **Honeypot.** `HoneypotField` is rendered in the sign-in/sign-up form, the forgot-password form and the checkout form. It is `aria-hidden`, `tabIndex={-1}`, `autoComplete="off"`, `spellCheck={false}`, 1×1 px, `overflow-hidden`, `pointer-events-none`, positioned at `-9999px` — **no pixels, no layout shift, no tab stop**. A non-empty value → `403 REQUEST_REJECTED` + event + ban + **revocation of the actor's active account session**.
- **CSRF forgery.** Every mutating API route now runs one central guard, `guardMutatingRequest()`, which verifies Origin + signed double-submit CSRF and records `csrf_forgery` on failure. The response is the same generic `403` a banned actor receives, so the shield never reveals which control caught the request.
- **Prototype pollution.** `readJsonBody()` now **rejects** (400) any body containing `__proto__`, `constructor` or `prototype` keys instead of silently stripping them, and the rejection is recorded as a tier-1 signal.
- **Webhook/OAuth state tampering** is covered by the existing HMAC/state verification plus this signal family; webhook routes authenticate by signature, not by Origin, and are excluded from the CSRF guard on purpose.

### 2.3 Tier 2 — suspicion (progressive cooldown, never permanent)

Signals: `rate_limit_abuse` — emitted whenever an auth bucket (`login`, `register`, `verify`, `resend`, `forgot`, `reset`, `2fa`, `reveal`) or promo validation is refused.

| Strike (within 24 h) | Cooldown |
| --- | --- |
| 1 | 15 min |
| 2 | 2 h |
| 3+ | 24 h |

Never permanent, and a strike never lengthens or shortens an existing tier-1 ban incorrectly: the effective expiry is the **later** of the current one and the new one, and a tier-2 strike can never promote an actor to a permanent ban.

### 2.4 Enforcement and anti-collateral rules

`shouldEnforceBan()` is the single decision point:

- An **IP** ban is enforced while active.
- A **fingerprint** ban is enforced only after **≥3 strikes** *and* never against a request that looks like an ordinary browser (`sec-fetch-mode` + `sec-ch-ua` + `accept-language` + a `Mozilla/5.0 …` user agent).
  Rationale: a header hash is shared by every visitor sending the same headers. Without a trusted IP there is no identity safe enough to hard-block, so the fingerprint path **records, escalates and deters** (404/403 on trap paths, cooldowns on mutations) but never locks a bystander out. Deployments that need real blocking set `TRUST_PROXY_IP_HEADERS=true` behind a proxy that overwrites `X-Forwarded-For`.
- A ban lookup error fails **open** for that single request (the handler's own query then fails closed at 503). Blocking every visitor during a database blip would be a worse failure.
- **Write amplification guard:** the same actor is recorded at most once per 15 s (bounded 5 000-entry in-process map, cleared when full). An unauthenticated probe flood cannot force a database write per request; the ban already exists and the response is identical.

## 3. Ephemeral-state hygiene

`src/lib/db/hygiene.ts` (`runEphemeralHygiene`) purges exactly the rows whose purpose expired — never accounts, live sessions, orders, order items, the wallet ledger, promo codes or the catalogue:

| Target | Rule |
| --- | --- |
| `google_oauth_states` | `expires_at < now` |
| `password_reset_tokens` | expired ≥ 7 days ago, or consumed ≥ 7 days ago |
| `pending_two_factor_challenges` | expired ≥ 24 h ago, or consumed ≥ 24 h ago |
| `security_bans` | lifted ≥ 7 days ago, or non-permanent and expired ≥ 7 days ago (active bans are never touched) |
| `carts` | `updated_at` older than 30 days (guest abandonment retention); items follow via `ON DELETE CASCADE` |
| `security_threat_events` | older than 90 days |

- Every statement is **bounded**: `DELETE … WHERE key IN (SELECT key … LIMIT n)`, default `n = 500` (`HYGIENE_POLICY.maxRowsPerRun`).
- Scheduling is throttled to **once per hour per process**, never concurrent, and runs inside `after()` from `GET /api/cart` and `GET /api/auth/session`, so a visitor never waits for maintenance. `EPHEMERAL_HYGIENE=off` disables it.
- A failure in one table never aborts the others, and nothing is thrown to the caller.
- The owner CLI can run it on demand (`npm run ops -- cleanup`).

## 5. Owner CLI (`npm run ops`)

`scripts/owner-ops.ts` — local terminal only. It refuses to run when `NEXT_RUNTIME` is set (i.e. inside the web app) or when a `window` exists, and no file under `src/app/**` imports it (asserted by test).

```
npm run ops -- inspect --limit 20
npm run ops -- bans list [--all]
npm run ops -- bans add --ip 203.0.113.7 --hours 24        # or --event <uuid>, --permanent
npm run ops -- bans lift --id <uuid> | --ip 203.0.113.7 | --ended
npm run ops -- bans account <email> --hours 24             # revoke sessions + ban its actors
npm run ops -- promo list | create … | toggle <code> on|off
npm run ops -- orders list [--status paid] | show <orderNumber>
npm run ops -- orders refund <orderNumber> [--reason "…"] [--dry-run]
npm run ops -- cleanup [--dry-run] [--limit 500]
```

Safety properties:

- Read-only unless the sub-command explicitly writes; `--dry-run` on refund/cleanup.
- A refund is **idempotent** (`wallet_ledger.idempotency_key = 'refund:<orderId>'`), writes a compensating `credit_refund` **credit** entry (never a ledger mutation — the 0008 trigger still forbids those), increments the wallet under `SELECT … FOR UPDATE`, marks the order `cancelled`, and writes an `owner_refund_issued` audit row — all in one transaction. Only `paid`/`fulfilled`/`completed` orders with an owning account and a positive total are refundable.
- Owner bans are always tier 1 (a deliberate decision), never depend on the automatic ladder, and write `owner_ban_created` / `owner_ban_lifted` / `owner_account_suspended` / `owner_promo_*` audit rows.
- Output never contains passwords, tokens, hashes or full addresses; ban keys are truncated in confirmation messages.

## 6. Operational requirements and residual risk

- **`TRUST_PROXY_IP_HEADERS=true` (with `TRUSTED_PROXY_HOPS` matching the real proxy chain) is required for hard blocking.** Without it, bans are recorded and escalated but a bystander that looks like a normal browser is never blocked. This is intentional: a header hash is not an identity.
- Bring `0009_security_threat_shield` up with `npm run db:migrate -- --dry-run` first, then the real run. The migration is additive only.
- `/admin` returning 404 is now the *only* admin surface answer; deleting rows/roles is not required. `users.role` and `ADMIN_EMAIL` remain but no web route consumes them for administration.
- The threat trail is bounded by retention (90 days) and the write throttle, but it is still an append-only table: monitor its size on high-traffic deployments.
- Not verified here: real PostgreSQL (integration tests skip without `TEST_DATABASE_URL`), a real reverse proxy/CDN in front of the app, Playwright, live SMTP/OAuth/payment.
- `security_threat_events`/`security_bans` are truncated by the destructive integration suite (see `src/lib/db/test-database.ts`), which is why the test-DB safety policy documents them.
