# S-26 — Dual-role sellers, isolated merchant portal, split-key vault v2 and dispute escrow

**Status:** IMPLEMENTED (local verification only) — 2026-11-25, branch `arena/8a1e76cc-web-stor`, built on `main` @ `1ba06df` (PR #26).
**Scope:** Wave 5B — customer/merchant onboarding, a server-enforced merchant portal, an impossible-to-transplant split-key envelope vault (v2) with buyer shredding and owner key rotation, plus buyer order disputes with automatic seller escrow freezes and local owner resolution.

## 1. Split-key envelope encryption v2 (digital vault)

### 1.1 Envelope

```
plaintext ──AES-256-GCM(DEK, AAD = record context)──▶ ciphertext
DEK       ──AES-256-GCM(KEK, AAD = context + kekId)──▶ wrapped_dek
KEK       = HKDF-SHA512(VAULT_MASTER_KEY, salt = VAULT_KEY_PEPPER, info = evora-vault-kek:v2:<keyId>)
```

- **Per-record random DEK.** Every sealed secret gets its own 256-bit `crypto.randomBytes(32)` DEK (`src/lib/security/vault-crypto.ts`). Two identical codes never share a ciphertext, a DEK or a wrapped DEK.
- **Split-key KEK.** `HKDF-SHA512` with the optional `VAULT_KEY_PEPPER` as salt. Without the pepper, an attacker holding a leaked `VAULT_MASTER_KEY` still cannot rebuild the KEK. The KEK is never stored; only its key id (`kek_id`) is.
- **Fail closed in production.** `resolveVaultKeyMaterial()` throws when `NODE_ENV=production` and `VAULT_MASTER_KEY` is absent or malformed, and `validateEnv()` (boot-time, S-17) lists `VAULT_MASTER_KEY` / `VAULT_MASTER_KEY_ID` as required. Development and tests get a **deterministic** (obviously non-secret, reproducible) fallback so unit tests never depend on ambient secrets.
- **Buffer hygiene.** Every temporary DEK, KEK, IV, tag and decoded field is zeroed with `.fill(0)` in `finally` blocks. No plaintext is ever logged.
- **Backward compatible reads.** `v1` rows (single shared `FULFILLMENT_ENCRYPTION_KEY`) stay readable; **every write is `v2`**. Allocation of a `v1` row upgrades it to `v2` in the same transaction.

### 1.2 Context-bound AAD (anti-transplant)

The payload AAD is the canonical record context:

```
evora-vault:v2:<productId>:stock            # unallocated stock
evora-vault:v2:<productId>:item:<itemId>    # allocated to a buyer's order line
```

- Stock is sealed with the `stock` context. On allocation the row is **re-sealed** with the buyer's context (`rebindVaultRowToBuyer`), so the AAD changes.
- Copying a ciphertext to another row, product, order item or account makes GCM authentication fail — mathematically, not by an `if` a future patch can delete. Proven in `tests/wave5b-db.test.ts` (a row moved to a second buyer's order line throws on open).
- The wrapped-DEK AAD (`evora-vault-dek:v2:<productId>:<identity>:<kekId>`) additionally binds the key id, so a wrapped DEK cannot be moved between records either.
- The payload AAD deliberately **excludes** the KEK id, which is what allows rotation to re-wrap only the 32-byte DEK and never re-handle plaintext codes.

### 1.3 Duplicate-code blind digest

- `code_digest = HMAC-SHA256(HKDF(VAULT_MASTER_KEY, "evora-vault-code-digest:v1"), normalize(code))`, hex.
- Normalization is NFKC + trim only: delivery codes are case-sensitive and must round-trip byte for byte. Control characters are refused.
- `fulfillment_vault_code_digest_idx` is a **partial unique index on `(product_id, code_digest)`**, so re-uploading an already-sold code (including a code that was later shredded) is rejected atomically by PostgreSQL. No plaintext is stored anywhere.
- The digest key is derived, so an attacker with database read access cannot brute-force short codes offline without the master key.

### 1.4 Cryptographic burn-after-reveal

`POST /api/account/orders/[orderId]/shred` (`guardMutatingRequest` + session owner check):

- the order must belong to the signed-in buyer and be `paid`/`fulfilled`/`completed` — a foreign `orderId` is indistinguishable from a missing one (`404`);
- **every** delivered row must already be revealed, otherwise `409 FULFILLMENT_NOT_REVEALED` (a buyer cannot destroy unread paid inventory);
- the row keeps `code_digest`, `revealed_at`, `shredded_at` and an immutable keyed `delivery_digest`, while `ciphertext`, `iv`, `auth_tag`, `wrapped_dek`, `dek_iv`, `dek_auth_tag` are set to `NULL`. The DEK is gone, so not even E-Vora can recover the code;
- idempotent (`alreadyShredded` on retry), and the database refuses resurrection: `fulfillment_vault_shred_is_permanent` rejects any update that puts ciphertext back on a shredded row.

UI: `/account/orders` gains a bilingual confirm-then-destroy action and a "permanently destroyed" status line.

### 1.5 Owner key rotation

`npm run ops -- vault rotate-keys [--dry-run] [--limit N]`:

- **re-wrap**: rows whose `kek_id` differs from the current key are unwrapped with `VAULT_MASTER_KEY_PREVIOUS` and re-wrapped with the current KEK — the ciphertext and its AAD are untouched, so rotation never decrypts a delivered secret;
- **upgrade**: `v1` rows are decrypted with the retired `FULFILLMENT_ENCRYPTION_KEY` (when configured) and re-sealed as fresh `v2` envelopes;
- rows whose retired key is not supplied are reported as `missing previous key` rather than guessed; `--dry-run` writes nothing;
- the run is recorded in `security_audit_log` (`owner_vault_key_rotation`).

## 2. Dual-role registration — zero buyer friction

| Path | Steps | Result |
| --- | --- | --- |
| **Customer (زبون, default)** | display name + email + password (or Google) — *no extra field* | `users` row, role `customer`. Existing Playwright selectors (`#auth-name`, `#auth-email`, `#auth-password`) unchanged |
| **Merchant (تاجر)** | the same account fields + store display name, normalized slug, optional bio, phone, country, terms | `users` row (role `seller`) **plus** a linked `seller_profiles` row with `status = 'pending'` (`0004` schema) created in the same transaction |

- `emailRegisterSchema.accountType` defaults to `customer`, so a client that never sends it is a customer.
- Store fields are re-validated server-side by `sellerApplySchema` (slug normalization, reserved words, phone/country shape, `termsAccepted === true`).
- A taken store slug rolls the **whole** signup back (`409 SELLER_SLUG_TAKEN`); no half-created merchant account exists.
- Existing customers — including Google-only accounts with no password — apply from `/seller` via `POST /api/seller/apply` (guarded, rate-limited, `pending` only).
- `/login` shows an explicit two-mode selector (`Customer` / `Merchant`) with bilingual copy (AR RTL / EN LTR). The merchant fields only exist in merchant mode.

## 3. Isolated merchant portal (`/seller`, `/api/seller/**`)

### 3.1 Tenant isolation (anti-BOLA / anti-IDOR)

- The seller id is resolved **only** from the authenticated session: `users.id → seller_profiles.user_id`. It is never read from a body, query string, cookie or JWT claim.
- Every helper in `src/lib/marketplace/seller-store.ts` takes `sellerId` as its first argument and puts `AND seller_id = $seller` in the SQL predicate. A cross-tenant read returns `undefined` → `404`; a cross-tenant write affects **zero rows**.
- Proven in `tests/wave5b-db.test.ts`: seller A cannot read, toggle or stock seller B's product; a cross-tenant stock import writes **no** vault rows at all (a merchant cannot poison a rival's deliveries).

### 3.2 Merchant security gate (red line)

A seller may only push anything **live** when **all three** hold, evaluated server-side on every request:

1. **Email verified** (`users.email_verified_at`),
2. **TOTP 2FA enabled and verified** (`user_totp.enabled_at` + `verified_at`),
3. **Seller profile approved** (`seller_profiles.status = 'approved'`, owner action only).

`/seller` renders a bilingual readiness checklist (✓/✕ per gate plus the first unmet hint). `requireLiveSeller()` refuses publishing a listing or importing live stock with `403 SELLER_GATES_INCOMPLETE` + `blocker` + the per-gate booleans. Un-publishing is allowed without the gate, so a merchant whose 2FA was disabled can still take their catalogue offline immediately.

### 3.3 Capabilities (once gated)

- `POST /api/seller/products` — create a draft listing: strict validation, integer-cent pricing (`1 … 10 000 000`), `inputType` (`none`/`player-id`/`region`/`activation-email`), server-generated unique slug. Listings start `is_active = false`.
- `PATCH /api/seller/products/[productId]` — toggle publishing (owner-scoped, `403` without the gate).
- `POST /api/seller/products/[productId]/stock` — batch-import up to 500 codes, sealed immediately as `v2` split-key envelopes with blind digests; duplicates reported, never overwritten.
- `GET /api/seller/summary` — gross sales, **10% platform commission** (`commission.ts`), escrow-held balance and payout-eligible balance (`payout-policy.ts`). Buyer identity, auth data and delivery secrets are never selected.
- `/seller` and every `/api/seller/**` response is `Cache-Control: private, no-store` (the portal path is in the proxy's private prefix list).

## 4. Order disputes, escrow freeze and owner resolution

Additive migration `0010_marketplace_sellers_disputes_and_vault_v2`:

- `order_disputes(id, order_id, user_id, reason, details, status, resolution_note, resolved_at, created_at, updated_at)` with
  - `status IN ('open','refunded','rejected')`, `reason IN (...5 reasons)`;
  - a **partial unique index** `order_disputes_open_order_idx ON (order_id) WHERE status = 'open'` — max one active dispute per order;
  - `order_disputes_closed_has_resolution` — a closed dispute must carry a resolution note and timestamp.
- `products.seller_id` (+ FK), `products.is_active`, `seller_profiles.payout_blocked_at/reason`, and the vault v2 columns.

Buyer endpoint `POST /api/account/orders/[orderId]/dispute`: guarded, session-owned order, `paid/fulfilled/completed` only, rate-limited, bilingual UI in `/account/orders`.

**Escrow freeze is immediate and derived, not denormalized:** `payout-policy.sellerPayoutLedger()` recomputes from order lines, so the moment a dispute is `open` the seller's entitlement moves from `payoutEligibleCents` to `escrowHeldCents`; a `cancelled`/`refunded` order is excluded entirely. `evaluatePayoutRequest()` refuses with `ESCROW_HOLD_ACTIVE` (or `PAYOUT_BLOCKED` once blocked).

Owner CLI (zero web admin):

```
npm run ops -- disputes list [--status open]
npm run ops -- disputes resolve <disputeId> --action=refund|reject --note="..."
npm run ops -- sellers list | approve <sellerId> | suspend <sellerId>
```

`resolve --action=refund` is atomic and idempotent inside one transaction: upsert + lock the buyer's wallet, insert exactly one `wallet_ledger` `credit_refund` (unique `idempotency_key = refund:<orderId>`), increment the balance, cancel the order, permanently stamp `payout_blocked_at/reason` on every non-platform seller in the order, and close the dispute. A replay reports `already resolved` and moves no money. `reject` closes the dispute, releases the escrow and moves nothing. `sellers suspend` also unpublishes that seller's listings.

## 5. Unchanged red lines

- **`/admin` is still an unconditional `404`** with `private, no-store`, an empty body, for anonymous and authenticated visitors alike. Administration remains local-only (`npm run ops`). Verified live and in the proxy probe.
- Customer checkout and registration remain frictionless; no buyer flow gained a step.
- `guardMutatingRequest()` (Origin + CSRF + active-ban check) runs on every new mutating route: seller apply, product create/toggle, stock import, shred, dispute.

## 6. Threat model notes / residual risk

- A merchant with a compromised **but 2FA-enabled, approved** account can still list products; that is the intended trust decision, mitigated by owner approval, per-listing drafts, and dispute-driven payout blocks.
- `VAULT_KEY_PEPPER` is optional. Without it the KEK depends on `VAULT_MASTER_KEY` alone; production guidance is to set both and to keep them in separate secret stores.
- Rotation requires the retired key to be present; a lost retired key makes unrotated rows unreadable (by design — no key escrow exists).
- Delivery digests prove *that* a specific code was delivered, not its value; they cannot be used for recovery.
- Real payment settlement, payout provider integration and browser E2E for the new pages remain NOT RUN in this environment (see `docs/VERIFICATION-LOG.md`).
