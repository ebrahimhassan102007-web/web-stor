# S-22 — Account recovery, password lifecycle, and two-factor authentication

**Status:** Implemented; local verification recorded on 2026-11-25. External-service and real-PostgreSQL verification remain NOT RUN (see `docs/BLOCKED.md` B-02).

## Delivered

- Additive PostgreSQL migrations `0005_password_reset_tokens.sql` and `0006_totp_two_factor.sql`; schema, migration runner and PGlite harness include the new tables. Tokens, TOTP state and recovery records are stored as digests or authenticated ciphertext, never as plaintext credentials.
- Password recovery uses expiring, single-use hashed reset tokens, a generic request response, bounded/rate-limited APIs and bilingual email templates. Password change verifies the current password, rejects password reuse, rotates the current session and revokes other sessions transactionally. Session management includes a revoke-other-sessions action while preserving the current session.
- Authenticated TOTP setup, enable, disable and recovery-code regeneration are exposed under `/api/account/two-factor/*`. Enrollment secrets are encrypted; activation requires a valid code; accepted TOTP counters are replay-protected; recovery codes are hashed, single-use, regenerated atomically, and revealed only once (10 per issuance). Sensitive actions require a current password or an active TOTP/recovery proof, with persistent rate limits and security audit events.
- Email/password login, verified-email completion, and Google OAuth callback issue a short-lived, hashed pending challenge when 2FA is enabled. They do not create a session until the challenge succeeds. The raw challenge exists only in an HttpOnly, SameSite=Lax cookie (Secure in production). Verification accepts a TOTP code in a ±1-step window or one unused recovery code, limits failed attempts, consumes the challenge atomically, then creates a fresh session and returns only a validated internal path.
- State-changing routes require both same-origin validation and an HMAC-signed double-submit CSRF token. `csrfFetch` attaches the token for auth, account, sessions, 2FA, cart and checkout requests; GETs remain non-mutating. Origin trust of forwarded headers is opt-in.
- Account security UI is localized in English and Arabic with correct LTR/RTL direction, theme tokens, setup instructions, copy controls and one-time recovery-code display.

## Operational notes

- Configure `TOTP_ENCRYPTION_KEY` as 32 bytes of hex and a stable `TOTP_ENCRYPTION_KEY_ID` before enabling 2FA in production. Preserve old key material for decryption/rotation until all corresponding records are re-encrypted or removed.
- Apply migrations only through the guarded, explicit migration command against the intended database. No production database was used during this work.
- Keep production `APP_ORIGIN`, `AUTH_SECRET`, mail transport, Google OAuth configuration and HTTPS cookie behavior aligned with deployment settings.
