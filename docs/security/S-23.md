# S-23 — Checkout integrity and encrypted digital fulfillment

**Wave 3A implementation record — 2026-11-25**  
**Status:** Implemented in code; local verification is recorded in `docs/VERIFICATION-LOG.md` after the end-of-wave checks. Production payment and real-PostgreSQL validation remain out of scope.

## Controls implemented

- Checkout orders are created inside a database transaction. The transaction locks the cart, cart lines, and product rows, validates current server-owned stock and prices, and computes totals with bounded integer cents. PostgreSQL uniqueness on the HMAC digest is the final concurrency guard for duplicate submissions. The raw client idempotency key is never persisted. A digest is scoped to the authenticated account; guest requests are scoped to their signed cart.
- Demo checkout remains explicitly unpaid and does not charge funds, decrement stock, clear the cart, or deliver codes. The storefront has no wallet ledger or real balance source; its documented demo balance is zero. `recordDemoOrder` rejects calls in production even if invoked outside the API route.
- Product stock/balance constraints prohibit negative values where those tables support them. No wallet debit or balance column was fabricated because the wallet is only a zero-balance display and there is no payment provider.
- Product-specific fulfillment targets are normalized and validated on cart writes and again at checkout. Validated target metadata is snapshotted to the order item, including player ID, region, and activation email.
- Digital inventory is stored as AES-256-GCM ciphertext with a key ID, IV, and authentication tag. The migration is additive (`0007_encrypted_fulfillment_vault.sql`); allocation locks available inventory and is designed to run inside the caller's paid-order transaction. Encryption keys are supplied through `FULFILLMENT_ENCRYPTION_KEY` and `FULFILLMENT_ENCRYPTION_KEY_ID`.
- Account order history never selects plaintext delivery codes. It shows a masked placeholder by default. A POST reveal endpoint requires the current account, matching order owner, same-origin plus signed double-submit CSRF, rate limiting, paid/fulfilled status, and a one-time atomic reveal marker. Successful replies are private/no-store and emit an audit event. Codes are decrypted only for that request and exposed with bilingual reveal/copy controls.

## Important boundaries

The current demo checkout is not payment confirmation. It intentionally cannot allocate or reveal fulfillment codes. A production payment integration must call vault allocation in the payment/order transaction only after verified payment, and must not re-use the demo-order path. Key rotation requires retaining decryption access for existing key IDs or an explicit re-encryption migration.
